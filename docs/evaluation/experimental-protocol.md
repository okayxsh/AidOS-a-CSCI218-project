# Experimental protocol

This protocol was fixed before the reported runs were generated. Changes made after looking at development output are listed in "Deviations and development runs" below.

## Questions

1. **Correctness (internal).** Does every policy return plans that satisfy the hard constraints, and does CP-SAT prove optimality for its stated objective?
2. **Optimisation success (internal).** Does AidOS achieve what its objective rewards (urgency-weighted coverage)?
3. **Behaviour (external).** How do the policies differ on measures that are not their objective: the worst-served zone, starvation, coverage spread, utilisation, and runtime? How do they respond to events?
4. **Information versus optimisation.** How much of any difference comes from using the urgency model (greedy vs FCFS), and how much from the optimiser (AidOS vs greedy)?

The evaluation cannot answer whether AidOS improves real humanitarian outcomes. The scenarios are synthetic, and the urgency model is a design assumption.

## Policies and frozen configuration

FCFS, urgency greedy, AidOS and AidOS balanced, as described in `policies.md`. Configuration (recorded in each run's `config.json`):

| Setting | Value |
|---|---|
| ε | 1 point |
| Resource weights | all 1 |
| Balanced floor target | 25% |
| CP-SAT time limit | 5 s total |
| CP-SAT workers | 1 |
| CP-SAT seed | 0 |
| Fuzzy configuration | `fuzzy_rules.json` v1.0 (Sugeno, 27 rules) |

No parameter of any policy or of the fuzzy model was changed during Stage 4. Nothing was tuned on evaluation data, so no development/test split is needed.

## Scenario families

Generated by `apps/api/aidos/evaluation/families.py`. The i-th scenario of a family has seed `seed_base + i` and its own `random.Random(seed)`, so every scenario is reproducible and families never share seeds.

| Family | Purpose | Zones | Resources | Stock per resource (share of requests) | Ratings | Requests |
|---|---|---|---|---|---|---|
| A | Low scarcity | 3–8 | 3–4 | 85–110% | uniform 0–10 | uniform 1–120, 10% zero |
| B | Moderate scarcity | 3–8 | 3–4 | 60–85% | uniform | uniform |
| C | Severe scarcity | 3–8 | 3–4 | 25–50% | uniform | uniform |
| D | Unequal urgency | 4–8 | 3–4 | 50–80% | half the zones 7–10 on every input, half 0–3 | uniform |
| E | Equal / near-equal urgency | 3–8 | 3–4 | 50–80% | one shared triple (probability 0.5 per scenario; 44 of 72 in the extended run) or ±1 per input | uniform |
| F | Unequal demand | 4–8 | 3–4 | 50–80% | uniform | 1–2 zones request 4–8× more |
| G | Multiple resource shortages | 3–8 | 4 | three resources 30–60%, one 100–130% | uniform | uniform |
| H | Dynamic events | base: family-B generator, seeds 800000+i | | | | |

Seed bases: A 100000, B 200000, C 300000, D 400000, E 500000, F 600000, G 700000.

Neutrality rules:

- Arrival order is the zone index. Zones are generated in random rating order (shuffled for D), so arrival order is independent of urgency and FCFS faces no systematic disadvantage.
- Every scenario of every family is reported. None are selected or dropped.
- Family means are pooled with equal weight (the same number of scenarios per family). The "all families" figures depend on this mix, so per-family results are always reported too.

## Dynamic scripts (family H)

**Recommendation mode** (`dynamic.recommendation_rows`): one session per script. Seven events are drawn from the current shared state with seed 800000 + i:

1. raise a random zone's severity (or time criticality) to 10;
2. add a new zone (ratings 6–10 / 4–10 / 6–10, requests 10–60 per resource);
3. lose 30% of one resource's stock;
4. a shipment of 20–80 units of one resource;
5. raise one request by 10–40;
6. advance time;
7. resolve one original zone.

All four policies are evaluated at every step on the same snapshot (verified: one outcome hash per step).

**Dispatch mode** (`dynamic.dispatch_run`): the same base scenario, with stock reset to 30% of requests. Script (seed 850000 + i):

1. lose 20% of one resource;
2. **dispatch**;
3. escalation;
4. a shipment of 15% of the requests, for each resource;
5. **dispatch**;
6. new zone;
7. second shipment;
8. **dispatch**;
9. a request increase;
10. third shipment;
11. **dispatch**.

Each policy runs its own trajectory, dispatching its own plan. Every event is valid whatever was dispatched before it, so all policies receive the identical script. Comparisons are paired by script; trajectories are not shared states.

## Scale and presets

| Preset | Static | Dynamic scripts | Timing repeats | Scaling study | Bootstrap resamples |
|---|---|---|---|---|---|
| smoke | 1 per family (7) | 2 | 1 | 5, 10 zones × 1 seed | 1,000 |
| standard | 20 per family (140) | 20 | 3 | 5–50 zones × 3 seeds × 3 repeats | 5,000 |
| extended | 72 per family (504) | 60 | 3 | 5–50 zones × 5 seeds × 5 repeats | 5,000 |

The standard preset took about 88 s and the extended preset about 279 s on the development laptop (durations recorded in each run's `manifest.json`), so the **extended run is the reported evidence**. The standard run is kept as an independent re-execution: it covers the first 20 scenarios and scripts of every family, and must reproduce the extended run's logical values exactly (`verify_results.py --against`).

## Statistics

- **Descriptive** (per policy, overall and per family): n, mean, sample sd, median, min, max, 10th/25th/75th/90th percentiles.
- **Paired comparisons** (`stats.paired`):
  - differences a − b on the same scenario (or the same script);
  - pairs with a missing value are dropped and counted;
  - reports wins/ties/losses (tolerance 1e-9), the mean and median difference, 95% percentile-bootstrap CIs (5,000 resamples, seed 20261111), and the paired effect size d_z = mean / sd of the differences.
- **Hypothesis tests** are limited to a pre-declared family of four, AidOS vs FCFS on:
  - urgency-weighted coverage;
  - lowest zone coverage;
  - starved zones;
  - the Jain index.

  The test is an exact two-sided sign test (no distributional assumption; ties excluded). p-values are Holm–Bonferroni adjusted within the family. All other comparisons are descriptive (CIs and effect sizes, no p-values).
- **Unit of analysis.** Scenario (static); script (both dynamic modes). Steps within a script are averaged before pairing.
- **Scope of inference.** The uncertainty describes variation **within the generator's distribution**, which was chosen by the authors. It does not generalise to real crises.

## Reproducibility

- **Recorded per run:**
  - `config.json`: the preset, family definitions, seed ranges, policy configuration and fuzzy version;
  - `manifest.json`: the run id, UTC times, duration, counts, failures, versions (engine, fuzzy rules, OR-Tools, NumPy, Python), platform, and a SHA-256 of every output file.
- **Overwrites.** A run directory is never overwritten: an existing run id is an error.
- **Determinism.** Logical values (plans, scores, metrics, outcome hashes) are deterministic for the same code and seeds. Timings are not.
- **Source revision.** The Stage 4 runs record "unavailable": the folder was not a git repository when they were produced. A local repository was initialised in Stage 5 (no commits yet); supplementary runs record `git rev-parse HEAD`, which is also unavailable until the first commit.

**Commands** (from `apps/api/`):

```bash
uv run python ../../experiments/run_benchmarks.py --preset extended
uv run python ../../experiments/verify_results.py <run_id> [--against <other_run_id>]
uv run --group analysis python ../../experiments/plot_results.py <run_id>
uv run python ../../experiments/report_results.py <run_id>
```

## Deviations and development runs

During development, smoke, standard and extended runs were executed to test the pipeline. Two problems found in them were fixed **before** the reported runs, and the development runs were deleted:

1. **Dispatch mode design.** In the first design the depot started with its full stock, so the first dispatch emptied it. Three of the five later dispatches had nothing to send, and the events between them could not influence anything. The script was changed to start at 30% stock with three supply waves.
2. **Dynamic statistics.** The first analysis paired dynamic comparisons by step, treating the steps of one script as independent and so understating uncertainty. Comparisons now use one value per script.

Neither change involved any policy or fuzzy parameter, and neither was chosen to favour any policy.
